## 二、整体方案：模块优先布局

### 核心变更

```
当前（节点优先）                    改为（模块优先）
nodes → computeLayout → positions   nodes → detectModules → moduleZones → nodesInZones
        ↓ 被动框台面                          ↓ 主动规划
        moduleLayoutInfo                      moduleZones + positions
```

### P0：模块检测规则审查和锁定

**当前 detectModule 逻辑**（viewer.html 第1921行附近）：
```javascript
function detectModule(nodeId) {
  for (var prefix in MODULE_PREFIXES) {
    if (nodeId.indexOf(prefix) === 0) return MODULE_PREFIXES[prefix];
  }
  return 'other';
}
```

**审查发现**：
- 当前只有4个有效前缀：`.hermes-`, `components-`, `data-`, `packages-port-tag-tool-`
- 26个节点无前缀→'other'
- 这个规则对当前数据够用，但对新项目需要自动发现（已有自动build模块配置的逻辑）

**锁定措施**：保持当前detectModule不变，但加一个模块列表验证函数，确保布局前模块信息是确定的。

### P1：other节点处理

26个other节点的构成：
| 类别 | 示例 | 数量 |
|------|------|------|
| 项目根目录文件 | package.json, vite.config.ts, README.md | ~10 |
| 平台目录 | plugins/, public/ | ~4 |
| 杂项 | 空字符串、重复条目 | ~12 |

**处理方式**：other节点不参与模块布局，放在`z=5`的一个独立薄层中，尺寸缩小30%，不透明度降低，视觉上表示为"游离节点"。

### P2：模块优先布局算法

**核心逻辑**：

```
1. 遍历所有节点，按 detectModule 分组
2. 每个有效模块（非other）：
   a. 根据成员数量确定台面大小（宽=数量*1.5+3，深=成员层级跨度*2+3）
   b. 按X轴从左到右排列模块台面（间距3.0）
   c. **多行换行**：一行放不下时（总宽>视口范围），自动换行到下一行，下一行Y轴偏移-4单位
   d. 台面Y位置 = 模块成员的平均层级Y
   e. 台面Z位置 = 0（居中），Z厚度=2
3. 节点在所属台面范围内散布：
   a. Y轴保持在模块的平均层级Y附近（±0.5）
   b. X轴在台面宽度范围内均匀分布
   c. Z轴在台面深度范围内均匀分布
   d. 穿模检测：在上述范围内做微调避让
4. 台面渲染：
   a. 透明度0.35，模块色填充
   b. 虚线边框，模块色
   c. 标签在台面上方2单位处
```

**LAYER的角色变更**：
- 不再是布局的第一维度
- 改为Y轴微调偏移：同模块内不同层的节点在Y轴上有±0.3的偏移
- 层级颜色保留：节点的层级色保留，模块色仅用于边框
- 层级信息通过hover/详情面板展示

### P3：跨模块粗管道

- 从源模块台面边缘（X边界+3.0）到目标模块台面边缘（X边界-3.0）
- 不经过节点，直接连接台面
- 粗管道（glow半径0.06，core半径0.035）
- 颜色渐变：源模块色→目标模块色
- 同一对模块之间的多条连接聚合成一条

### 定量验收标准

| 指标 | 目标值 |
|------|--------|
| 相邻台面间距 | ≥2.5单位 |
| 模块内节点密度 | 节点间距≥1.2单位 |
| Z轴范围 | ≤6单位 |
| 台面透明度 | 0.35 |
| 跨模块管道数量 | 与模块间实际连接数一致 |
| other节点位置 | 独立薄层，不干扰模块区 |

### 新旧布局切换

在 viewer.html 顶部添加：
```javascript
var USE_MODULE_LAYOUT = true;  // false = 使用旧布局
```

false时完全回退到当前computeLayout逻辑。

## 四、风险（完整版）

| 风险 | 概率 | 影响 | 缓解 |
|------|:----:|:----:|------|
| other节点放置不当影响整体布局 | 低 | 中 | 独立薄层，z=5远离主体 |
| 模块布局后穿模仍然存在 | 中 | 高 | 定量目标约束+USE_MODULE_LAYOUT可回退 |
| 旧布局依赖的force-layout同步 | 中 | 中 | USE_MODULE_LAYOUT开关保障两套并存 |
| **双代码路径维护成本** | 中 | 中 | 仅在过渡期保留两套，稳定后移除旧布局代码 |
| **性能影响**（模块布局计算量大于旧布局） | 低 | 低 | 50节点规模下可忽略，如超过100节点考虑缓存 |
| **模块检测歧义**（新项目的前缀规则不同） | 中 | 中 | P0锁定检测规则，新项目需重新配置MODULE_PREFIXES |
| **新旧布局渲染结果不一致导致主公困惑** | 高 | 低 | 默认启新布局，旧布局仅用于调试回退 |

## 五、验证步骤（新增）

每个P阶段完成后执行：
- P0完成：`node -e "检测逻辑验证"` 输出模块成员列表，与预期对比
- P1完成：打开页面查看other节点是否在独立薄层，不干扰模块区
- P2完成：截图测量台面间距≥2.5、节点间距≥1.2、Z范围≤6
- P3完成：检查跨模块管道是否从台面边缘到台面边缘，颜色渐变是否正确
