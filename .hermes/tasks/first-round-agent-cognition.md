### Task 2：生成 Agent 认知标注数据（赵公明手动 + 读代码）

#### 2.1 工作范围量化
| 项目 | 估算 |
|------|------|
| 扫描对象 | arch-scanner 项目自身（约 30 个目录 + 150+ 文件） |

| 预计耗时 | 约 30-45 分钟 |

#### 2.2 Agent 诊断判定标准

##### 节点状态（status）

| 状态 | 判定条件 | 示例 |
|------|----------|------|
| **risk** 🔴 | ①扇入+扇出 > 20；②有循环引用；③单节点承载跨3个模块以上的数据流转；④零连接但非目录/资源节点（工具遗漏） | 枢纽节点、单点故障节点 |
| **warning** 🟡 | ①扇入或扇出 > 10 但 < 20；②跨2个模块流转；③依赖图中位于长链路中间（层级过深） | 高负载节点、长路径中间节点 |
| **healthy** 🟢 | 以上条件都不满足 | 普通叶子节点、标准服务节点 |

##### 节点角色（role）

| 角色 | 定义 | 判定条件 |
|------|------|----------|
| **hub** | 枢纽节点 | 扇入+扇出 > 15，或连接了 ≥3 个不同模块 |
| **bridge** | 桥梁节点 | 连接2个模块，是两个模块间唯一的或主要的通信路径 |
| **leaf** | 叶子节点 | 扇出 = 0，只被调用不调用别人 |
| **normal** | 普通节点 | 不满足以上任何条件 |

##### 模块状态（module.status）

| 状态 | 判定条件 |
|------|----------|
| **overloaded** 🔴 | 模块内节点数 > 10，或模块间连接数 > 20 |
| **needs-split** 🟡 | 模块内节点数 > 6 且承担了2种以上不同职责 |
| **healthy** 🟢 | 以上都不满足 |

#### 2.3 颜色编码规则（status 与 role 的优先级）

**规则：status 为主色调，role 为点缀/边框色。**

```
节点主体颜色 = status（healthy=绿, warning=黄, risk=红）
节点边框颜色 = role（hub=金#FFD700, bridge=紫#9C27B0, normal=白, leaf=灰）
```

当 status=risk 且 role=hub 时：主体红色 + 金色边框 → "风险枢纽节点"
当 status=healthy 且 role=bridge 时：主体绿色 + 紫色边框 → "健康桥梁节点"

**完整色表：**

| 维度 | 取值 | 颜色 | Hex |
|------|------|------|-----|
| status | healthy | 绿色 | #4CAF50 |
| status | warning | 黄色 | #FF9800 |
| status | risk | 红色 | #F44336 |
| role | hub | 金色 | #FFD700 |
| role | bridge | 紫色 | #9C27B0 |
| role | normal | 白色 | #FFFFFF |
| role | leaf | 灰色 | #9E9E9E |
| module | healthy | 绿色 | #4CAF50 |
| module | overloaded | 红色 | #F44336 |
| module | needs-split | 橙色 | #FF5722 |

#### 2.4 数据校验设计

viewer.html 读取 `agentDiagnosis` 字段时：
- 字段缺失 → 默认 `healthy` + `normal`，不阻塞渲染
- 格式错误 → console.warn 告警 + 使用默认值
- 极端情况无诊断数据 → 整体 fallback 到当前无诊断版本的渲染行为

#### 2.5 Suggestions 格式模板

每条建议遵循 `[类型] 建议正文` 格式：

```
[架构] 将 user-service 拆分为 auth-service 和 profile-service 两个独立模块
[性能] 建议在 api-gateway 层增加缓存中间件，减少直连调用
[风险] module-core 承载了40%的数据流转，建议拆分
[维护] 移除未使用的 dep-xxx 依赖
```

#### 2.6 输出 JSON 格式

```json
{
  "nodes": [
    {
      "id": "xxx",
      "name": "...",
      "agentDiagnosis": {
        "status": "risk" | "warning" | "healthy",
        "role": "hub" | "bridge" | "normal" | "leaf",
        "summary": "节点诊断一句话摘要",
        "detail": "详细诊断说明（2-3句）",
        "suggestions": ["[类型] 建议1", "[类型] 建议2"]
      }
    }
  ],
  "modules": [
    {
      "name": "xxx",
      "agentDiagnosis": {
        "status": "overloaded" | "healthy" | "needs-split",
        "summary": "模块诊断一句话摘要",
        "detail": "详细诊断说明",
        "suggestions": ["[类型] 建议1"]
      }
    }
  ],
  "global": {
    "score": 7.5,
    "issues": ["问题1", "问题2"],
    "suggestions": ["[全局] 建议1", "[全局] 建议2"]
  }
}
```

### Task 3：3D 监视器详情页改造（Codex 执行）

#### 3.1 详情页分拆

**当前问题：** 节点详情和模块详情共用一个详情页面。
**改造方案（主公提出的布局）：**

```
┌─────────────────────────────────────────────┐
│  上端：图例区（可折叠，默认展开）             │
│  ├ 节点图例 ── 枢纽/桥梁/叶子/普通           │
│  ├ 模块图例 ── 健康/过载/建议拆分            │
│  └ 状态图例 ── 正常/警告/风险               │
├──────────────┬──────────────────────────────┤
│  左侧：模块详情  │  右侧：节点详情             │
│  （双击模块弹出）│  （单击节点弹出）           │
│  模块名 / 职责   │  节点名 / 角色             │
│  包含N个节点     │  连接数 / 所属模块          │
│  Agent诊断      │  Agent诊断                 │
│  建议列表        │  建议列表                  │
├──────────────┴──────────────────────────────┤
│  底部：全局诊断区域                           │
│  架构评分 / 全局问题清单 / 全局优化建议         │
└─────────────────────────────────────────────┘
```

**交互规则：**
- 单击节点 → 右侧弹出节点详情
- 双击节点 → 模块详情 + 该节点自动高亮
- 双击空白处 → 关闭所有详情面板
- 模块详情和节点详情可同时显示

#### 3.2 图例改造
- **可折叠**：点击图例区域标题可折叠/展开，折叠后只显示一行图标和箭头
- **拆分平铺**：图例拆为三行（节点角色/模块状态/健康状态）平铺在上端
- **默认展开**，用户可折叠释放空间
- 详情页打开时如果遮挡图例，图例自动折叠

#### 3.3 Agent 诊断数据注入
- viewer.html 从 `__EMBEDDED_DATA__`（已有数据注入路径）读取诊断数据扩展字段
- 诊断数据与现有节点/模块数据松耦合：数据主体的 `agentDiagnosis` 为可选字段
- 无诊断数据时 viewer 行为不变（向下兼容）

#### 3.4 性能兜底
- 节点数 < 500：全部渲染诊断颜色和标注
- 节点数 ≥ 500：诊断标签使用 LOD（每帧检查距离，远距离不渲染诊断细节）

### Task 4：颜色编码改造（Codex 执行，与 Task 3 合并执行）

基于 2.3 节的颜色编码规则，修改节点渲染：

- 模块台面颜色 ← module.status
