# 3d-monitor 下一阶段议题讨论 — 模块详情页 / 排布策略 / CodeGraph参考

## 议题一：模块详情面板

**现状**：点击模块台面没有任何反应。节点点击有详情面板（显示文件路径、端口等），但模块没有。

**需求**：点击模块台面（或模块标签），弹出模块详情面板，展示：
- 模块名称
- 成员节点列表（可点击跳转）
- 模块间连接概览（来自/去往哪些模块）
- 成员数量、层级分布等统计

**选项**：
A. 复用现有的节点详情面板（nodeInfoPanel），在点击模块台面时切换显示模块信息
B. 独立模块详情面板（另起一个panel）
C. 展开台面（点击后台面放大，内部节点散开显示详情）

**初步意见**：选A。复用现有面板逻辑简单，用户点击节点→节点详情，点击空白/台面→模块详情。

## 议题二：模块排布策略

**现状**：一字平铺（多行换行），每个模块占一行。当前4个模块+other节点，一行够用。

**问题**：如果项目有8-12个模块，一字排开会很宽，多行排版会很高，3D空间利用率低。

**选项**：
A. 当前方案（一字多行）— 简单，可读，但空间利用率低
B. **鱼骨/树状布局** — 按模块间依赖关系排列（依赖多的模块居中），参考力导向布局
C. **层次化布局** — 按层级（layer）分区，每个区内的模块再排列
D. **动态缩放** — 模块少时放大间距，模块多时缩小间距，自适应

**参考CodeGraph**：CodeGraph 没有布局算法（它不输出3D可视化），但它的图谱结构（nodes + edges + groups）可以指导布局。

**初步意见**：先做D（动态缩放）+ 优化多行间距，保证8个模块也能整洁排列。B（鱼骨/树状）是更高级的优化，可后续迭代。

## 议题三：CodeGraph 参考价值

**CodeGraph 的能力**：
| 维度 | CodeGraph | 我们（port-tag-tool） |
|------|-----------|----------------------|
| 解析引擎 | tree-sitter AST（20+语言） | acorn AST（JS/TS）+ 正则 |
| 框架识别 | 17个Web框架路由（Django/FastAPI/Express等） | 无 |
| 存储 | SQLite + FTS5全文搜索 | JSON文件 |
| 可视化 | 无（纯文本/JSON） | **3D拓扑图（Three.js）** |
| 增量扫描 | FSEvents监听+自动re-index | 无 |
| 模块分组 | 目录前缀自动分组 | 前缀匹配（detectModule） |

**可借鉴的点**：
1. **tree-sitter 解析引擎** — 比acorn更准，支持更多语言
2. **框架路由识别** — 识别17个框架的路由，可以让我们知道"这个API是FastAPI的router"
3. **SQLite存储** — 支持增量扫描和全文搜索
4. **自动同步** — 文件变化时自动更新图谱

**关键是**：CodeGraph 是给AI Agent用的（查代码、搜依赖），arch-scanner 是给人看的（3D架构图）。两者互补，不是替代。

**建议**：不直接使用CodeGraph的代码（外部参考），但可以借鉴它的模块识别逻辑来改进我们的 detectModule——特别是框架路由的识别能力。
