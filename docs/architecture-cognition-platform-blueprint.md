## 一、项目定位：从"架构扫描器"到"架构认知平台"

### 1.1 项目是什么

**架构认知平台**（Architecture Cognition Platform）是一个通用的架构认知引擎——
不限于代码，任何有结构、有节点、有关系的领域（组织架构、经济架构、股权架构等），
都可以接入并得到"扫描 → 认知 → 诊断 → 可视化"的全流程服务。

### 1.2 原始目标

让**不懂技术的人**能够看懂项目架构。

### 1.3 升级目标

让不懂技术的人**能够对架构做判断和决策**。
不止是"看到"架构，而是能"读透"架构——知道哪里好、哪里有问题、怎么改。

### 1.4 更高定位

架构认知平台 = 通用引擎，不同领域换前端识别工具：

```
┌──────────────────────────────────────────────────┐
│  领域A：代码架构        领域B：组织架构   领域C：股权架构   │
│    port-tag-tool          组织扫描工具      股权扫描工具     │
│         ↓                     ↓                ↓         │
│   ┌──────────────── Agent 认知加工 ─────────────┐       │
│   │  读数据 → 理解架构 → 诊断风险 → 给出建议     │       │
│   └──────────────────────┬──────────────────────┘       │
│                          ↓                               │
│   ┌─────────── 可视化表达（3D监视器）───────────┐        │
│   │  主镜头：现状 → 子镜头N：方案对比              │        │
│   │  详情页：Agent诊断 + 行动建议                 │        │
│   └──────────────────────────────────────────────┘      │
└──────────────────────────────────────────────────┘
```

核心命题：**不同领域换前端识别工具，后面的认知加工和可视化是共通的。**

## 二、三层架构（核心模型）

### 第1层：领域识别工具（Data Engine）

| 领域 | 工具 | 状态 |
|------|------|------|
| 代码架构 | port-tag-tool v0.2.0 | ✅ 可用，需维护 |
| 组织架构 | 待设计 | ❌ |
| 经济/股权架构 | 待设计 | ❌ |
| 其他领域 | 按需扩展 | ❌ |

**port-tag-tool 当前能力**（v0.2.0）：
- AST 解析引擎（acorn+acorn-jsx）扫描 import/require
- 跨目录相对路径支持（`../data/systemData` → `data--systemData`）
- npm 依赖自动识别、配置文件解析
- MCP 协议适配（5个 tool）
- 迭代方向：按功能需求扩展识别范围，或增加新工具

### 第2层：Agent 认知加工（核心价值层）

**这是整个平台最有价值的环节。**

#### 2.1 认知加工的输入
- 工具扫描的结构化数据（节点/连接/端口/标签）
- Agent 直接读代码/文档的理解
- 历史架构诊断经验（未来通过 RAG 沉淀）

#### 2.2 认知加工的输出

| 层级 | 输出物 | 说明 |
|------|--------|------|
| 节点级 | 节点角色标注 + 健康状态 + 风险诊断 | 正常/枢纽-高风险/枢纽-高价值/异常 |
| 模块级 | 模块归属 + 功能描述 + 负载评估 | 健康/过载/耦合过高/建议拆分 |
| 全局级 | 架构评分 + 问题清单 + 优化建议 | 多方案可选，含影响分析 |
| 认知报告 | 面向人类的架构解读 | 文字+3D图示+方案对比 |

#### 2.3 认知加工的技术演进

```
当前（纯LLM推理）：
  port-tag-tool 数据 + 我直接读源码 → 一次性输出诊断
  → 局限：每次从头分析，没有积累

近期（RAG + 诊断模式库）：
  把每次诊断沉淀为"架构特征→诊断结论→优化建议"模式
  下次遇到类似架构，直接匹配历史模式
  → 技术选型：本地向量库（DuckDB + embedding）足矣

中期（图数据库 + 多Agent编排）：
  用图数据库（Neo4j）存储架构知识
  图查询直接算："核心节点""最长链路""故障影响范围"
  LangGraph 编排多 Agent：扫描/诊断/可视化生成分工

远期（跨领域通用引擎）：
  抽象出"架构图元"通用模型
  任何领域只要定义好节点/关系/规则，即可接入
```

### 第3层：3D 可视化展示（认知传达层）

#### 3.1 当前能力

| 能力 | 状态 |
|------|------|
| Three.js 内联渲染 | ✅ |
| 节点散点布局 + 模块优先布局 | ✅ v0.1.40-node-spread.22 |
| 跨模块粗管道 + 模块内细管道 | ✅ |
| 流向箭头动画 | ✅ |
| 枢纽高亮 | ✅ |
| 三轴语义（Y层级/X领域/Z内外） | ✅ |
| 图例 | ✅ |
| 模块详情面板（双击弹出） | ✅ |

#### 3.2 升级方向：从"展示数据"到"展示认知"

**现状的问题**：详情页只展示原始数据（"name: xxx, connections: 12"），
没有 Agent 的认知和判断。

**目标**：详情页成为 Agent 认知的载体

```
📍 节点：user-service
├ 状态：🔴 风险节点（连接数全模块最高，38条）
├ 原因：承担了3个模块的全部数据流转
├ 诊断：单一故障点——此节点宕机会导致3个模块瘫痪
├ 建议：① 拆分为两个服务 ② 或引入缓存层
└ 影响范围：点击查看受影响的3个模块
```

**3D 空间的认知体现**：

| 视觉元素 | 表达什么 | 状态 |
|----------|----------|------|
| 颜色编码 | 健康/风险/异常/待观察 | 需设计 |
| 节点边框 | 枢纽/关键/普通 | 已有部分 |
| 标注气泡 | Agent 诊断摘要 | 需新增 |
| 详情页 | Agent 完整诊断+建议 | 需重做 |
| 子镜头 | 多方案对比 | 需设计 |

#### 3.3 子镜头方案对比（交互范式）

这是主公提出的核心设计：

- **主镜头**：当前架构现状（静态快照，带 Agent 标注）
- **子镜头1-N**：Agent 给出的不同优化方案
  - 每个子镜头只显示**方案涉及到的节点和链路**
  - 不涉及的节点在子镜头中隐藏，聚焦展示
  - 附带文字描述：调整内容、预期效果、潜在风险
  - 主镜头和子镜头可并排对比

示例：
```
主镜头：模块A连接了15个节点，耦合严重 → 标注 🔴

子镜头1：拆分为 A1 和 A2
  展示拆完后 A1→A2 的链路变化
  文字："拆分后单模块负载降低40%，但增加跨服务通信"

子镜头2：引入中间代理层
  展示代理层插在中间的效果
  文字："引入网关后A的直连数从15降到3，延迟增加~5ms"

子镜头3：保持现状+风险监控
  标注风险等级和监控建议
```

## 三、Agent 角色定位

### 3.1 赵公明的职责

在架构认知平台的框架下，赵公明的角色从"调度者"升级为"架构分析师"：

| 职责 | 说明 |
|------|------|
| 调用工具扫描 | 调度 port-tag-tool 或其他领域工具 |
| 交叉验证数据 | 工具输出 + 我直接读代码，互相校验 |
| 理解架构意图 | 不只看节点连接，还要理解"为什么这么连" |
| 识别风险点 | 枢纽节点、单点故障、过长链路、耦合度过高 |
| 推演优化方案 | 给出 1-3 个方案，含影响分析 |
| 生成认知报告 | 文字+3D图示，面向非技术人类 |
| 标注3D图 | 把诊断结果可视化在 3D 监视器上 |
| 沉淀到skill | 每次诊断经验回写到诊断模式库 |

### 3.2 Agent 认知的"存在感"

主公的质疑：**Agent 在 3D 图上没有存在感。**

解决方案：
- 3D 空间上：颜色编码 + 标注气泡 + 边框标记
- 交互层面：点击节点弹出 Agent 诊断（不是原始数据）
- 对比层面：主镜头现状 + 子镜头方案 = Agent 在"说话"
- 报告层面：认知报告作为独立产物，与 3D 图互相引用

## 四、应用场景与商业模式

### 4.1 应用场景

| 场景 | 用户 | 价值 |
|------|------|------|
| **个人项目认知** | 开发者自己 | 快速理解自己或别人的项目 |
| **团队代码审查** | 技术Leader/架构师 | 定位耦合点、技术债、重构方向 |
| **新人入职速通** | 新入职开发者 | 3D 图 + 认知报告快速上手 |
| **技术债评估** | CTO/技术VP | 量化架构健康度，辅助决策 |
| **组织架构分析** | 管理者 | 看清团队分工、汇报链路、沟通瓶颈 |
| **股权架构分析** | 投资者 | 看清持股关系、资金流向 |
| **通用服务** | 外部用户 | 拿项目来扫，输出3D报告（SaaS模式） |

### 4.2 商业模式（远期）

```
阶段一：开源社区
  → 项目开源，积累用户和认知诊断模式

阶段二：MCP Server 分发
  → 作为 MCP Server 提供给 Claude Desktop / Cursor 等
  → 按调用量收费或订阅制

阶段三：SaaS 平台
  → 上传代码/组织数据 → 在线生成 3D 架构报告
  → 免费版：单项目扫描 + 标准诊断
  → 付费版：多项目 + 深度诊断 + 历史追踪
```

## 五、市场调研结论

### 5.1 竞品矩阵

| 项目 | 代码分析 | 3D可视化 | AI诊断 | 开源 | 活跃 | 多语言 |
|------|:--------:|:--------:|:------:|:----:|:----:|:-----:|
| **我们** | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| CodeGraph | ✅ | ❌ | ❌ | ✅ | ✅ | 有限 |
| ArchGuard | ✅ | ❌ | ❌ | ✅ | ✅ | ✅ |
| Structure101 | ✅ | ❌ | ❌ | ❌ | ✅ | ✅ |
| SoftVis | 有限 | ✅ | ❌ | ✅ | ❌ | 有限 |
| CodeCity | 有限 | ✅ | ❌ | ✅ | ❌ | 有限 |
| Claude Code | ✅ | ❌ | ✅ | ❌ | ✅ | ✅ |
| Codex CLI | ✅ | ❌ | ✅ | ❌ | ✅ | ✅ |

### 5.2 核心发现

**市场空白（蓝海）：** 目前没有工具同时具备"代码扫描 + 3D 可视化 + AI 诊断"三者。

**最近似参考：**
- **ArchGuard**（Thoughtworks）— 架构分析管线最完整，但缺 3D 和 AI
- **SoftVis/CodeCity** — 3D 可视化概念最接近，但无 AI，已停更
- **Claude Code** — AI 理解架构最强，但无可视化
- **Structure101** — 架构治理最成熟，但高价、无 AI、无 3D

**差异化优势：**
- 唯一将"AI自动分析 + 3D可视化 + 架构诊断"三者合一
- MCP 生态位先发机会
- Web 原生，无需安装

**需警惕：**
- Claude Code / Copilot 未来可能加可视化
- AI 诊断准确性要持续验证（否则不如规则引擎靠谱）
- 3D 可视化必须是"沟通工具"而非"炫技"

### 5.3 结论

有继续做下去的必要，方向明确，竞争力清晰。

## 六、第一轮行动规划

### 目标

跑通**代码架构领域**的完整闭环，让主公看到"加了 Agent 认知的 3D 图"和现在的有什么不同。

### 具体步骤

```
Step 1：修复 MCP 路径
  → 将 port-tag-tool 的 MCP 注册指向当前 arch-scanner 目录

Step 2：选一个项目（推荐 arch-scanner 自己）
  → port-tag-tool 扫描
  → 我读代码验证数据
  → 我输出带认知诊断的标注数据

Step 3：改造详情页
  → 从"静态数据展示"改为"Agent 诊断 + 建议"
  → 增加颜色编码（红/黄/绿）
  → 增加标注气泡

Step 4：生成新版 3D 图
  → 注入带 Agent 标注的数据
  → 主公验收效果

Step 5：沉淀到 skill
  → 将完整流程写成可复用的 skill
```

### 不做的（第一轮）

- ❌ 不搭 RAG / 图数据库（后面的迭代再加）
- ❌ 不做 MCP Server（先跑通内部闭环）
- ❌ 不做子镜头方案对比（那是升级版的功能）
- ❌ 不做跨领域（先聚焦代码架构）
